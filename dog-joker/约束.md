# 《夺狗囧事》桌游助手 - 开发约束

## 1. 技术约束

- **单文件架构**：全部代码（HTML + CSS + JS）必须写在 `index.html` 一个文件中，不允许拆分、引入外部依赖或使用构建工具
- **零依赖**：不引入任何第三方库、框架、字体文件或 CDN 资源
- **运行方式**：双击 HTML 文件即可在浏览器中直接运行，无需本地服务器
- **存储限制**：localStorage 当前处于禁用状态，每次刷新页面从初始状态开始；后续若启用，仅用于断点续玩，不得存储敏感信息
- **移动端优先**：所有交互必须在竖屏手机上可操作，触摸目标尺寸不小于 44px；桌面端作为兼容场景

## 2. 游戏逻辑约束

### 2.1 胜负判定
- 成功条件：累计翻开 ≥3 张 ❌️（揭发者本人仅需 ≥2 张）
- 失败条件：被翻出 🐶
- 获胜：累计 2 次成功；多人同时达成则共同获胜
- 出局：累计 3 次失败
- 终局：有人达到 2 次成功，或仅剩 1 名未出局玩家
- 同一轮中，一名玩家不会同时获得成功和失败；成功的前提是本轮未被翻出 🐶

### 2.2 卡牌与翻牌
- 每位玩家固定 5 张牌，编号对应门号 1~5
- 每轮开始时所有卡牌重置为背面（`back`），上一轮的翻开状态不继承
- 已被翻开的牌在本轮内不可再次被揭发
- 翻牌顺序严格遵循「玩家优先」：从领袖开始按顺时针遍历玩家，每位玩家内部按门号升序翻牌
- 全员 OK 结算时，翻出 🐶 立即终止后续玩家的翻牌

### 2.3 领袖机制
- 领袖由 ⭐️ 标记，与普通卡牌状态无关
- 领袖首次行动必须选门（强制），后续轮到时与其他玩家一样四选一
- 领袖不可揭发自己
- 揭发操作通过 `leaderIdxOverride` 锁定目标领袖索引，防止中间状态漂移导致揭发对象错误
- 「再开一扇」和「重新开门」会夺取领袖标记并重置 okPlayers

### 2.4 结算触发
- 仅三种情况触发结算：揭发出 🐶、全员 OK、领袖面前已翻开 ≥3 张 ❌️
- 揭发出 🐶 时，只翻开被揭发的那张牌，不额外翻开其他玩家对应门位的卡牌；成功判定基于各玩家当前已翻开的 ❌️ 数量
- 非 OK 操作（揭发 ❌️）会将该玩家从 okPlayers 中移除（保留"最后一次操作为OK"的语义）
- 再开一扇/重新开门发生时，无论是否换领袖，okPlayers 全部清空
- 当所有存活非领袖玩家均在 okPlayers 中时，触发全员 OK 结算
- 领袖面前累积翻开 ≥3 张 ❌️ 时，立即进入结算（不等全员 OK）

### 2.5 重新开门可用性
```
canReopen = (openDoors.length > 0)
  && ((5 - openDoors.length) >= (openDoors.length + 1))
```
即剩余未开门数必须 ≥ 当前已开门数 + 1，否则该选项禁用。

## 3. UI/UX 约束

### 3.1 交互流程
- 所有玩家操作前必须先展示桌面阵容 + 底部行动按钮，点击按钮后才弹出操作弹窗
- 点击弹窗外部遮罩区域可关闭弹窗，回退到上一步
- 门栏在整个搜查阶段及待结算状态始终可见
- 无传手机遮罩页面、无音效、无震动反馈

### 3.2 结算提示（pending-settlement 阶段）
- 满足结算条件时，不立即弹出结算弹窗，而是进入 `pending-settlement` 阶段
- 底部显示文字提示「当前轮因「XXX原因」将进行结算」+ 【查看结算】按钮
- 在用户点击【查看结算】之前，桌面阵容的牌保持未翻开状态，用户可查看当前桌面布局
- 仅在首次点击【查看结算】时执行翻牌、胜负计算和弹窗展示
- 此设计确保用户在结算前有机会观察当前桌面阵容

### 3.3 视觉规范
- 暗色主题（背景 #1a1a2e），卡牌使用对比色区分状态
- 已翻开的牌使用绿色底色（#2a4a3a）+ 绿色边框（#4a8）
- 背面牌使用 45° 条纹图案
- 🐶 牌在结算阶段有脉冲动画（pulse）
- 当前行动玩家行高亮（红色半透明背景 + 发光阴影）
- 已出局玩家行降低透明度（opacity: 0.4）

## 4. 状态管理约束

### 4.1 Phase 枚举
合法 phase 值及其含义：
| Phase | 说明 |
|-------|------|
| `setup` | 选择玩家数量 |
| `hiding-ready` | 等待当前玩家点击按钮进入藏狗 |
| `hiding` | 藏狗弹窗打开中 |
| `searching-ready` | 等待当前玩家点击按钮进入搜查行动 |
| `searching` | 行动弹窗打开中 |
| `pending-settlement` | 结算条件已满足，等待用户确认查看结算 |
| `settlement` | 结算弹窗展示中 |
| `gameover` | 终局弹窗展示中 |

### 4.2 状态字段完整性
- 每次新增状态字段时，必须同步更新 `defaultState()`、`initGame()` 和 `startNewRound()` 三处初始化位置
- `settlementInfo` 仅在 `confirmSettlement()` 执行后写入，`pending-settlement` 阶段使用 `pendingSettlement` 暂存触发信息
- `pendingSettlement` 在结算确认后清空为 null

### 4.3 渲染触发
- 所有状态变更必须通过 `StateManager.set()` 进行，该方法自动调用 `Renderer.render()`
- 禁止直接修改 `_state` 对象后手动调用渲染

## 5. 代码组织约束

- 代码分为三个命名空间对象：`StateManager`（状态）、`GameLogic`（逻辑）、`Renderer`（渲染）
- `GameLogic` 只负责状态计算与变更，不直接操作 DOM
- `Renderer` 只负责读取状态并渲染 UI，不修改游戏状态
- 事件处理函数（onclick 等）可以调用 `GameLogic` 方法，但不应包含业务逻辑
- 新增功能应遵循现有模式，不引入新的全局变量或顶层函数
